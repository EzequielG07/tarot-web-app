Arquitectura Segura: Supabase, JWT y Row Level Security (RLS)

Este informe técnico detalla los principios de defensa en profundidad, control de acceso basado en roles (RBAC) y seguridad criptográfica implementados en la base de datos de Anita Tarot.

1. El Paradigma Backend-as-a-Service (BaaS) y Zero Trust

En el desarrollo web tradicional, la base de datos confía en un servidor backend centralizado (Node, Python, Java). El backend filtra las consultas con cláusulas WHERE. Si un desarrollador olvida un filtro o comete un fallo de autorización (vulnerabilidad IDOR / BOLA), cualquier atacante puede manipular registros.

En Supabase, aplicamos el principio de Zero Trust (Confianza Cero): la seguridad se delega directamente en el motor de PostgreSQL mediante políticas criptográficas evaluadas a nivel de cada fila individual.

Principio Fundamental: No importa si un atacante accede directamente a la API REST de la base de datos usando Postman, cURL o un script en Python; PostgreSQL rechaza la petición en el propio kernel de la base de datos si no cumple con las políticas de Row Level Security.

2. ¿Por qué es seguro exponer la `Anon Key` en el frontend?

Es común que auditores de seguridad novatos marquen la variable NEXT_PUBLIC_SUPABASE_ANON_KEY como un hallazgo de "fuga de credenciales". Sin embargo, esto es un falso positivo por las siguientes razones técnicas:

  • Rol `anon`: La clave anónima es simplemente un identificador de proyecto que asigna al usuario el rol de invitado sin privilegios.
  • Aislamiento total con RLS: Con Row Level Security activo, el rol anon solo puede ejecutar las operaciones explícitamente autorizadas (en nuestro caso, solo SELECT).
  • La clave crítica es `service_role`: La clave service_role secret tiene privilegios de superusuario para saltarse el RLS (bypassrls). Esa clave NUNCA debe exponerse en el cliente.

3. Row Level Security (RLS) a Bajo Nivel

Cuando ejecutamos:

ALTER TABLE public.servicios_precios ENABLE ROW LEVEL SECURITY;

PostgreSQL activa un interruptor de seguridad estricto: la tabla queda completamente bloqueada para cualquier rol no privilegiado.

Desglose de las Políticas Implementadas:

A. Política Pública de Lectura:

CREATE POLICY "Permitir lectura publica de precios" 
ON public.servicios_precios FOR SELECT 
USING (true);

El predicado USING (true) indica que cualquier usuario del mundo puede leer las filas de la tabla para visualizarlas en el sitio web.

B. Política Restringida de Modificación (Solo Admin):

CREATE POLICY "Permitir modificacion solo a usuarios autenticados" 
ON public.servicios_precios FOR UPDATE 
TO authenticated 
USING (true)
WITH CHECK (true);
  • TO authenticated: La consulta solo es válida si la cabecera HTTP incluye un token JWT firmado por Supabase Auth con el claim role: 'authenticated'.
  • WITH CHECK (true): Valida que los datos modificados cumplan con las restricciones de la base de datos antes de persistir.

4. Matriz de Mitigación de Amenazas (OWASP Top 10)

Amenaza (OWASP) Escenario de Ataque Mitigación Implementada
Broken Access Control (A01:2021) Un usuario malicioso envía un UPDATE vía HTTP para cambiar tarifas a $0. RLS descarta la petición a nivel de motor de PostgreSQL al no poseer el rol authenticated.
Injection (A03:2021) Inyección SQL en campos de texto (ej. ' OR '1'='1). PostgREST convierte automáticamente los datos en consultas parametrizadas seguras.
Cryptographic Failures (A02:2021) Intercepción de contraseñas o tokens en tránsito. Tráfico cifrado de extremo a extremo mediante TLS/HTTPS y contraseñas hasheadas con bcrypt.
Privilege Escalation Un atacante modifica su JWT localmente para asignarse el rol `authenticated`. Postgres valida la firma criptográfica HMAC-SHA256 del JWT contra la clave privada del servidor.
